# Architecture and boundaries

## Layers aligned to the team problem

| Layer | Responsibility | Implementation | Value |
| --- | --- | --- | --- |
| Workflow surfaces | Explicit commands and readable context/handoffs | bin/agentbridge.js | Meet developers in their existing workflow |
| Collaboration domain | Criteria, ownership transfer, decisions, findings and status | lib/core.js | Shared understanding across people and agents |
| Execution coordinator | Durable run start/end, separate roles, bounded attempts, recovery | lib/workflow.js | Know whether work actually ran, failed or stopped |
| Verification | Revision/snapshot checks, criterion coverage, latest batch, separate review | core.js + git.js | Explain completion eligibility and stale evidence |
| Durable storage | Atomic task aggregates, optimistic version check, local locks | lib/store.js | Preserve findings and reject conflicting writers |
| Adapters | Native CLI protocols, Git and subprocess execution | providers.js, git.js, process.js | Replaceable provider interfaces; no credential proxy |

The CLI calls domain operations. The coordinator calls domain/storage operations and adapters. Providers return data; they never call verification or acceptance transitions. Storage does not depend on provider behavior. A future MCP surface should call the same domain functions rather than introduce a second source of truth.

## Team model and scale direction

The domain target is a project with many people, agent sessions and tasks. A task has one accountable owner at a time; this is not a one-person or two-person limit on the project. The current actor fields and sequential handoffs do not hardcode Alice/Bob or limit the number of names. They do not yet provide a participant directory, collaborator memberships, independent human reviewer assignments or multi-approver policy.

Planned extensions should distinguish people, provider identities and individual agent runs; represent task collaborators, reviewers and dependencies explicitly; and scope context to relevant work. Ownership, implementation, review and approval are roles rather than fixed slots assigned to two people. A provider is not a teammate identity.

Before claiming larger-team support, replace the project-wide execution bottleneck with task/workspace-scoped coordination and explicit shared-resource conflict rules, and validate cross-clone updates, ownership transfer races, fan-out/fan-in reviews and recovery without lost history. Per-task locking alone will not solve cross-task code conflicts. Establish distributed conflict semantics before optional hosting; a cloud backend is not a prerequisite for the product model.

The current schema and local lock are a bounded first implementation. Two-person tests establish that scenario only; no throughput, participant capacity or distributed consistency guarantee is inferred.

## Incremental decisions

Retain JavaScript ES modules, Node's test runner and zero npm dependencies. The existing small prototype does not justify a simultaneous TypeScript or database migration. Split process, Git, provider, storage and coordinator concerns out of core.js. Add types when public contracts stabilize or consumers require them.

Use one atomic JSON aggregate per task. Embedding decision, finding, receipt and history records prevents partial task/decision/evidence transactions and eliminates references to missing private evidence. Each mutation reads under a short project write lock, writes a synced temporary file and atomically renames it. The public saveTask API compares versions to reject stale writes. History is append-only by convention through commands, not cryptographically immutable. Power-loss guarantees beyond atomic replacement depend on the filesystem; there is no distributed transaction manager.

A separate project execution lock serializes local agent/test runs. Ownership transfer and configuration changes are blocked during active runs; new findings may still be recorded and preserved. Locks and worktree paths are local. Cross-machine ownership conflicts still require Git synchronization and explicit merge resolution. No distributed lease or automatic semantic merge is implemented. Do not claim simultaneous independent clones are globally serialized.

## Record location

`store.locate(cwd)` resolves, in order: `<checkout>/.agentbridge` (repository mode); `AGENTBRIDGE_RECORDS` (absolute, environment mode); the pointer `<git-common-dir>/agentbridge.json` containing an absolute `recordsDir` (shared mode). The Git common directory is the same for every linked worktree, so all worktrees resolve to one record set and one set of locks; agents only need read access to the pointer and write access to the records directory. `init --records-dir` refuses relative paths, non-Git directories, checkouts with in-repository records and repositories that already have a pointer; it joins an existing schema-2 record directory instead of resetting it and writes the pointer only after the records are valid. Shared mode is single-machine: records are not in Git history and are not synchronized between people.

## Shared and private data

- `.agentbridge/project.json`: schema version.
- `.agentbridge/project-decisions/<decision-id>.json`: one shared record per project-wide decision with proposer, acceptor, supersession links and history. Separate files keep independent proposals from colliding in Git. Acceptance of a superseding decision atomically marks the prior one superseded under the project write lock; two proposals superseding the same decision cannot both be accepted locally. Cross-clone acceptance races still surface as Git conflicts.
- `.agentbridge/tasks/<task-id>.json`: shared aggregate containing criteria, owner, pending handoff, declared path scope, decisions, findings, review summaries, execution receipts, test plan, verification and attributed acceptance, history and optimistic version.
- `.agentbridge/local/`: ignored lock files, workspace mappings, raw provider output, raw test logs and migration backups.
- `.agentbridge/evidence/`: old v0.1 private evidence remains ignored.

Task IDs use UUIDs; legacy eight-hex IDs remain readable. Schema-1 projects require explicit `migrate`; old tasks are backed up privately, available decisions/evidence are embedded, missing artifacts become unavailable records, and legacy reviews cannot satisfy the new gate. Migration does not fabricate success. Raw review backup remains private.

Commit and exchange `.agentbridge` records through normal Git review. Never commit raw logs. A fresh clone can read handoffs immediately. To execute or validate current-code equivalence it must attach a checkout containing the implementation revision. Missing workspaces produce an explicit unresolved reason.

## Agent coordination contract

`lib/coordination.js` serves agents typed, compact views over the same domain records; it adds no second source of truth. `inbox` returns owned open tasks with next action and open-finding count, pending handoffs in both directions, active scopes owned by others, accepted and proposed project decisions, and the latest 50 history events by other actors on tasks the actor is involved in. With `--since last` it records a private per-actor cursor and filters changes and accepted decisions to those after it; outstanding work is always listed. `check` maps each path (repository-relative, or absolute from any worktree of the same repository, resolved through the nearest existing directory) against active tasks' scopes and reports conflicts, the actor's own coverage, and unclaimed paths. An actor covers paths of tasks owned by itself, by its person (`alice` for `alice/codex`) or or, for a person, by their own agents; sibling agents of one person conflict. Active means effective status other than `done`, `done-unchecked`, `merged` and `cancelled`; `stale` remains active because its completion no longer holds. Scope matching lives in `lib/scope.js`: plain entries match the path or its descendants; an entry ending in `*` is a string prefix. `*` elsewhere is rejected.

`lib/agents.js` adapts the same functions to agent tooling. `hook pre-edit` reads a Claude Code or Codex `PreToolUse` payload (Codex `apply_patch` paths are read from the patch's `Add/Update/Delete File` and `Move to` headers), resolves the edited files to its repository top level, and exits 2 with the conflicts when `check` disallows it; files outside a repository, repositories without records, and non-edit tools pass. Record errors block, so a broken record set is visible rather than silently unguarded. `mcp` is a dependency-free, newline-delimited JSON-RPC MCP server (tools capability only) whose actor is fixed at launch. Task arguments accept 8-character ids. `resume` (CLI and the `resume_task` tool, and the result of `handoff_receive`) is a bounded packet for continuing work: goal, criteria, next step (pending handoff, merged PR, open findings, stale checks, verified-awaiting-acceptance, else the recorded next action), the task's code branch (the latest non-default branch its events were recorded on) with head, commits ahead of and files changed against the default branch (at most 30), a PR (merged, or mentioned in the note and marked merged when the cached list says so), accepted and pending decisions, open findings, the last three evidence entries, overlapping work by other parties (at most 5), and record freshness. `report_finding` and `resolve_finding` call the same domain functions as the CLI. `lib/review.js` builds the person's to-do list from the same records: offers to them, proposed project decisions, verified work of theirs or their agents, open tasks of theirs with the same title (the person's own copy is kept), their tasks whose PR merged (one batch question), their agents' in-progress tasks idle 24h or more (close or move to another of their agents), and their tasks overlapping an earlier in-progress claim by another party. Bare `agentbridge` in a terminal, outside an agent session, in an initialized repository, asks about each with one key and calls the same domain functions (acceptances go through the signing path); `agentbridge todo` does the same reading answers from standard input. Unanswered items change nothing. Claims (`start_task`, `set_scope`, `handoff_receive`, `task add --scope`, `assign --scope`, `task scope`, `handoff receive`) first run a synchronous `sync` when records sync through the branch, auto-sync is on and the last sync is over five seconds old, waiting up to five seconds for a running sync's lock; if the remote is unreachable the claim proceeds with a warning that names the last sync time. Overlap is then refused under the write lock, and moving a task to `in_progress` refuses paths that another party's earlier open task holds. The write lock waits up to 15 seconds for another process (such as a background sync) and removes a lock left by a dead process on the same host. A race between clones that both claim before either pushes is not prevented; the board flags the later of two open tasks held by different parties over overlapping paths, with the commands that settle it. The pre-commit check acts as an explicit `AGENTBRIDGE_ACTOR`, else the agent session, else a known actor named by the branch prefix, else, in a team clone, the person's GitHub login. `lib/digest.js` (`digest`, CLI and MCP tool) is the catch-up: it syncs first, then lists, since a time (default the actor's last digest, kept in `local/digest-cursors.json`, else seven days; `--peek` keeps the cursor), merged tasks grouped by PR, cancelled and accepted tasks, handoffs with their outcome, accepted and pending decisions, findings opened and still open, open work by owner (changed first) with the linked PR's state from one `gh pr list --state open`, the cached merged list, or `gh pr view` for at most five PRs named in notes, open PRs linked to no task, and the to-do list of the person (for an agent, its person). It writes nothing but the cursor. `lib/team.js` gives people the team-wide views over the same records: `board` (active tasks grouped by owner, offers not yet accepted, proposed decisions, verified work awaiting acceptance, and attention reasons: stale, needs work, open findings, in-progress without scope, and, when `origin` is on GitHub, a planned, in-progress or needs-work task whose recorded code branch, or a branch or "merged PR #N" named in its latest note, matches a merged pull request; the merged list is one `gh pr list` call cached for ten minutes in `local/merged-prs.json`, and the board never changes a status), `log` (all task and project-decision history, newest first, filtered by actor and time), assignment (`task add --to` creates then offers; the assigner owns the task until the assignee receives it; the recipient can `handoff decline`, the offerer or owner can `handoff withdraw`, and the owner can `task cancel` with a reason, a closed status that releases scope and reopens through `in_progress`; a person may withdraw or cancel for their own agents, `login` for `login/<agent>`, only outside an agent session, and the event records `for` the owner), and PR publication through the GitHub CLI (one marker-identified comment per task, updated in place, plus an `agentbridge` commit status whose success requires acceptance at the PR head revision). Onboarding (`lib/onboard.js`) composes existing operations: a version line (package version against the repository's `package.json` through `gh`), records (`init`, or `init --records-dir ~/.agentbridge/records/<repo>-<hash>` with `--solo`), `setup` (team only), `hook install-git`, skill symlinks into `~/.claude/skills` and `~/.codex/skills`, the same `PreToolUse` and `UserPromptSubmit` entries in Claude Code settings and `~/.codex/hooks.json` (existing AgentBridge hook commands are rewritten to the absolute Node path, because a hook that fails to start lets the edit through), and an appended Codex `[mcp_servers.agentbridge]` block. In team mode with an `origin`, in-repo records are moved with `setupSync`, and when `origin` is on GitHub and the person is a repository admin, a ruleset named "AgentBridge records: append-only" (deletion and non-fast-forward on `refs/heads/agentbridge-records`, no bypass actors) is created once, found again by name. Skill symlinks that point at another install are repointed; real directories are left alone. Each step is idempotent, skipped when the tool's home directory is absent, and reported; edited config files get a one-time `.bak-agentbridge` copy. Commands use the absolute path of the stable `node` on PATH rather than a versioned install path.

Identity (`lib/identity.js`): `setup` stores the `gh api user` login as `agentbridge.login` in local Git config and registers the `agentbridge` merge driver; records directories carry `.gitattributes` with `*.json merge=agentbridge`. When a login is configured, the CLI, MCP server and hooks resolve actors before calling the domain: empty or `me` → the login; a known agent name → `login/agent`; the login or `login/...` pass; anything else is refused. Recipients (`--to`) resolve agent names the same way and pass other names through. Acceptance (`accept`, `decision accept`, `resolve-merge`) refuses agent actors. The core stays identity-agnostic.

Record merge (`lib/merge.js`): a three-way merge over top-level fields. Arrays of objects with `id` (history, findings, decisions, reviews, implementations, runs, evidence) are unioned by ID with per-item three-way comparison; history is time-ordered. `version` becomes max+1, `updatedAt` the latest, `note` the latest by time. Other fields take the one-sided change; same-field disagreements keep ours, are listed in `mergeConflicts` with base, ours and theirs, and make the driver exit non-zero so Git reports the conflict. Any mutation of a record with `mergeConflicts` is refused until `resolve-merge` settles each field.

`hook prompt` (Claude Code `UserPromptSubmit`) prints only incoming handoffs, newly accepted decisions and others' changes since the actor's cursor, and nothing otherwise. `hook pre-commit` checks staged paths, including deletions, against active scopes; the committer comes from `AGENTBRIDGE_ACTOR`, the agent session, a branch prefix already known as an actor, or the GitHub login in a team clone; an unidentified committer (a solo clone outside an agent session) is warned, not blocked. `hook install-git` writes a marked wrapper into the repository's hooks path and moves any existing hook to `pre-commit.agentbridge-next`, which runs after a passing check. `task scope` lets an owner set paths later and refuses overlap with other owners' active work. Task notes are owner-written status lines (at most 200 characters for new notes) recorded in history and shown in the inbox beside owned tasks and other owners' scopes.

Contracts are versioned (`v: 1`) and published as JSON Schema in `schema/agentbridge.v1.schema.json`; tests validate real outputs and stored records against it. Event attribution: every event carries `actor` when a person caused it; legacy `handoff_offered` events without `actor` are attributed to `from`.

## Execution contract

Provider request: `{provider, kind: implement|review, cwd, prompt, artifactDir, timeoutMs}`.
Implementation result: `{summary}`. This is an agent claim, saved privately; no test or acceptance consequence follows from its wording.

Recorded implementation (`implement record`): for work done in an interactive agent session or by hand. Requires a clean task workspace with commits beyond the base revision, the task owner as actor, a tool label (`claude|codex|human|other`) and a summary. It stores an attributed claim bound to the observed revision and code digest, counts toward the three-attempt bound, and is reviewed and tested exactly like an AgentBridge-run implementation. The tool label is self-reported; a review must use a provider different from a `claude` or `codex` label.

Provider timeouts default to 30 minutes for implementation and 10 minutes for review, configurable per run within 1 s–2 h. Binary resolution order: `AGENTBRIDGE_<PROVIDER>_BIN` (absolute executable), then `PATH`, then known app bundles (the Codex CLI inside the macOS ChatGPT app).
Review result: `{outcome: pass|needs_work, summary, findings: [{description, severity: low|medium|high}]}`. Malformed or contradictory output fails the run. A needs-work result must have a finding. Each finding gets a stable ID and remains open until explicitly resolved.

Codex uses `exec`, workspace-write for implementation, read-only for review, ephemeral sessions, a final-message file, and a JSON output schema for review. Claude uses print mode, JSON output, no persisted session, `dontAsk`, explicit file-tool allowlists and an empty strict MCP configuration; review only gets Read/Glob/Grep, implementation additionally gets Edit/Write. Neither adapter requests permission bypass. Normal provider configuration and managed policy can still affect execution. Existing installed CLI authentication remains provider-owned.

Official interfaces checked 2026-11-21:
- https://learn.chatgpt.com/docs/non-interactive-mode
- https://code.claude.com/docs/en/cli-reference

The installed CLIs' help and version availability were inspected. No authenticated model call is implied by those checks. Contract tests mock provider replies. Implementation may fail closed when tools are denied. External execution remains trusted-project only; file-tool restrictions are not equivalent to an OS sandbox.

Subprocess contract: executable plus argv, no implicit shell; return exit code, signal, reason, bounded stdout/stderr and duration. Timeout, output overflow and cancellation terminate the POSIX process group. Spawn failure and provider error are recorded, never treated as success. Windows descendant termination is not qualified.

## State and evidence

Typical path:

`planned → in_progress → implemented → ready_for_review → verified → done`

Any open finding or failed execution yields `needs_work`. Starting another implementation invalidates acceptance. Review opinions and individual test outcomes are persisted independently of the task status. Three implementation attempts per task bound retries; after that, stop and create a follow-up task. There is no background automatic retry or autonomous fix loop in v0.2.

Work happens in a created or explicitly attached Git worktree/checkout. The implementation command leaves changes for a person to inspect and commit. Review compares the task's base commit to the complete current committed diff, including committed additions/deletions. Dirty tracked, staged and untracked code blocks review/test. Patches over 200 KB are rejected rather than truncated. Submodules are unsupported and rejected by snapshot creation.

Receipts bind to the exact observed commit plus a digest of tracked paths, file modes and Git blob IDs excluding `.agentbridge/`. A snapshot is captured before the test batch and checked after each command; after review it is checked again. Both commit and code digest must remain unchanged during an execution. Review also records base commit and patch digest. Current eligibility compares code digests, so committing collaboration metadata does not invalidate unchanged code. The UI must still show the original evidence commit; it must never imply a new execution at the newer metadata commit. Ignored dependencies, external services and ambient environment are not part of this code digest and limit reproducibility.

Verification requires a successful implementation, a current passing review from a different provider tied to that implementation, no open findings, a successful latest complete configured test batch, unchanged test configuration, and declared checks covering every criterion. Manual attestations do not qualify. Declared criterion coverage is a human mapping, not proof that test assertions fully capture the requirement. Human acceptance is a separate owner-attributed command after verification.

People get four commands; the rest serve agents and scripts. `assign` creates or takes a task and, when the recipient is the person or one of their own agents, reassigns it directly; otherwise it makes a handoff offer (a person may offer their own agent's task). `done` closes a task: with `--reason` it cancels, a verified task is accepted, otherwise it closes it as `merged` after checking the PR. Both run only outside agent sessions. Without `--actor`, a person is their GitHub login (`agentbridge.login` in team mode, `agentbridge.person` saved by `onboard --solo`, else the system user name). `task reassign` changes a task's owner in one `reassigned` event (from, to, reason, acting person). It runs only outside agent sessions, by a person who is the owner or the owner's person, and only to that person or their own agents; work for another person still goes through a handoff offer. The board flags `in_progress` tasks with scope and no event for 24 hours; it never reassigns. `merged` and `cancelled` are stored closed statuses that release paths and reopen through `in_progress`. `task close` sets `merged` only after `gh pr view` reports the pull request merged, and records its number, merge time, branch and URL in a `closed_merged` event; it is not human acceptance. Status is derived on read: a historical verified/done state becomes `stale` if current evidence checks fail. When the only unmet check is that no workspace is attached in this checkout, status is `done-unchecked`/`verified-unchecked`: shared receipts qualify, but current-code equivalence was not evaluated locally. History is preserved. No model can promote itself through a structured review response; local operators can still edit files or impersonate actor names, so stronger policy boundaries remain future work.

## Recovery and sharing

Run start is saved before launching a child. Ordinary failures finalize the run. If the parent crashes, `activeRun` and any lock remain; no automatic replay occurs. `recover` checks the lock owner process has stopped on this host, records interruption and returns to needs_work. Inspect partial files before retrying. A surviving child may need manual termination after an abrupt parent crash; worktrees are retained.

Across clones: share both implementation commits and task records, receive the handoff, attach the relevant revision, and resume from persisted state. Resolve Git conflicts with both histories visible. Automatic union of histories, live team presence and cross-clone conflict detection are roadmap items, not current capabilities.

## Provenance

`store.event` appends a `by` stamp to every task and project-decision event: `via` (`terminal`, `agent`, `mcp`), the detected agent and session id (`CLAUDECODE`/`CLAUDE_CODE_SESSION_ID` for Claude Code, `CODEX_THREAD_ID`/`CODEX_SANDBOX` for Codex, `AI_AGENT` for others), and the numeric GitHub id from `agentbridge.githubId` in local Git config (written by `setup`, and by `onboard --solo` without renaming actors). The same detection limits the CLI actor to the session's agent, refuses person-only commands inside any agent session, and names the committer for the pre-commit check. Detection is environment-based and is not authentication.

`lib/signing.js` signs approval events (`decision_accepted`, `human_accepted`, `merge_resolved`, `policy_changed`) at creation through a signer that `store.event` calls when a person command runs, so a failed signature aborts the write. The signed message is `agentbridge-approval v1` plus canonical JSON (sorted keys) of the record id and the event without its `sig`. Verification resolves the numeric GitHub id to a login, builds an `allowed_signers` file from that login's GitHub SSH signing keys, and runs `ssh-keygen -Y verify`. Tests use throwaway keys and run with an isolated global Git config, so they never touch the developer's keys.

## Records branch sync

`lib/sync.js` keeps team records on the `agentbridge-records` branch, checked out as a worktree at `<git-common-dir>/agentbridge-records` and linked with the existing shared-records pointer, so every worktree and code branch of a clone reads one record set and code branches never carry records. `sync` fetches, then under the records write lock commits local changes with plumbing (`write-tree`, `commit-tree`, `update-ref`, so code hooks do not run on record commits), fast-forwards or merges the remote branch file by file with `mergeRecords` against the merge base, releases the lock, and pushes; a rejected push retries up to three times. `sync --init` creates the branch (an empty root commit) or attaches to the remote one, and moves committed `.agentbridge/` records into it, staging their removal from the code branch for the person to commit. When the remote branch already has records, a clone that still holds its old committed copy folds it in instead: files missing on the branch are added, records whose history is already on the branch are skipped as stale, and others are merged with `mergeRecords` against the newest branch revision whose history the old copy contains, so only real disagreements become frozen conflicts. Mutating CLI commands and MCP tool calls start a detached sync when records changed; the prompt hook and MCP reads start one at most once a minute to pull. `git config agentbridge.autoSync false` turns this off. After each successful push the clone stores the pushed commit in `local/remote-seen`; on the next sync, if that commit is not an ancestor of the fetched remote branch, sync stops before merging. `--accept-rewrite` skips the check once; the clone's own history is then merged into the rewritten branch, so dropped records return.
